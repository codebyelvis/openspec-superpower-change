## ADDED Requirements

### Requirement: Native instructions expose profile-aware implementation gates

Managed native instructions SHALL expose the existing compact local Direct
Change exception to generic Preflight language. Inline readiness, required
verification and inline self-review SHALL suffice only under that exception's
bounded conditions. Compact external execution, standard/strict work,
multi-slice work and protected effects SHALL retain their required standalone
gates. Behavioral evidence, Major approval and independent Review requirements
SHALL NOT be weakened by a platform default or a compact label.

#### Scenario: Compact local editorial correction

- **WHEN** an obvious local reversible correction satisfies Direct Change's
  compact exception and changes no protected boundary
- **THEN** the managed instructions permit inline readiness and self-review
- **AND** required verification remains mandatory without inventing a separate
  Plan or Preflight merely because a file changes

#### Scenario: Compact external execution

- **WHEN** compact work is dispatched under an external Handoff
- **THEN** the local inline exception does not waive its required Preflight,
  assignment, bound evidence or completion boundaries

#### Scenario: Unapproved Major rule change

- **WHEN** a proposed change affects workflow, approval, routing or evidence rules
  and its exact OpenSpec contract has not been approved
- **THEN** implementation remains blocked even when native tool permission exists

### Requirement: Native defaults preserve request and artifact ownership

Native consumer instructions SHALL preserve Router-owned method selection and
the ordinary-question and standalone read-only advisory exceptions. A required
plan SHALL be formed or reused before execution. Authorized user/project
destinations and existing immutable bindings SHALL take precedence over native
directory defaults; an incompatible binding change SHALL require new contract
approval instead of silent relocation.

Standalone advisory SHALL default to chat. Explicitly requested persistence
SHALL return to Router classification before writing and honor an applicable
native publisher without conferring gate authority. Governed external evidence
SHALL retain its assigned product, role, instance, bound attempt paths and exact
contract format. A native publisher SHALL NOT rename, rewrite or replace bound
external evidence. Unsupported product substitution SHALL remain rejected.

#### Scenario: Native review rule requests saving every review

- **WHEN** the current request is standalone read-only advisory without an
  explicit persistence instruction
- **THEN** the response remains in chat without creating a Handoff or report file

#### Scenario: User requests an advisory file with a native publisher

- **WHEN** a previously chat-only advisory is explicitly requested as a file
- **THEN** Router classifies persistence before writing
- **AND** the destination and publisher contract must be compatible or the
  conflict is reported without bypassing publication protection
- **AND** the saved advisory cannot sign Preflight or advance canonical state

#### Scenario: Platform plan directory conflicts with a bound plan

- **WHEN** a native rule defaults to `docs/design/` but the reviewed contract
  already binds another plan destination
- **THEN** the applicable plan is available before execution at the bound path
- **AND** no duplicate or relocation changes the binding

#### Scenario: Claude launcher uses a different backend model

- **WHEN** `claudex` or `claudeg` supplies advisory input through Claude Code
- **THEN** its real product remains Claude Code
- **AND** it cannot substitute `codex` or `grok-cli` in a schema-6 assignment

### Requirement: Runtime qualification distinguishes products from actual entries

Qualification evidence SHALL distinguish product, launcher, actual configuration
root, native instruction sources, discovered skill paths, dependency path/hash
and delivery policy. An empty private skills directory SHALL NOT alone prove
missing shared discovery. Another account's parity SHALL NOT prove this entry's
native loading, behavior or authority. Content consumers SHALL NOT acquire
formal roles merely by sharing source bytes.

The existing four-target portable synchronization SHALL remain responsible for
its selected files and managed blocks only. Outside native bytes SHALL remain
unchanged. Alternate accounts and native rules/hooks/configuration SHALL require
a separate exact path/prestate adaptation plan and appropriate approval;
portable target retargeting and identity-whitelist widening SHALL NOT substitute
for that plan. Native behavior SHALL require sufficient native event evidence;
file parity and inspected compatibility flags alone SHALL NOT imply it.

#### Scenario: Alternate account discovers a shared skill

- **WHEN** the active account's catalog lists a shared skill absent from its
  own private skills directory
- **THEN** discovery evidence records that shared source
- **AND** neither the absence nor a default-account hash result decides active
  body loading, behavioral acceptance or control-plane authority

#### Scenario: Four targets match but a consumer entry is unverified

- **WHEN** all four portable targets pass hash/discovery checks but an alternate
  account or linked consumer lacks behavioral evidence
- **THEN** portable parity may be reported for its exact scope
- **AND** seven-entry behavioral acceptance remains pending or blocked

#### Scenario: Grok imports a Claude-only publisher hook

- **WHEN** inspect registers a hook restricted to Claude launchers in native Grok
- **THEN** this is recorded as a compatibility risk rather than a reproduced
  enforcement failure
- **AND** any isolation change requires its own supported native mechanism,
  exact reviewed mutation, acceptance and rollback
- **AND** the portable sync does not edit native hooks or broaden the publisher

#### Scenario: Native configuration adaptation is requested during sync

- **WHEN** a requested correction would edit outside a selected portable file
  or four-target managed block
- **THEN** the synchronization phase stops for the separate scoped adaptation
  contract instead of silently copying personal configuration

## MODIFIED Requirements

### Requirement: Mandatory review correction loop

Every implementation path outside the compact local Direct Change exception
SHALL complete a current-revision Preflight Review, verification, and
post-implementation Review before completion. The compact local exception
SHALL retain inline readiness, required verification and inline self-review;
it SHALL NOT apply to compact external execution, standard/strict work,
multi-slice work or protected effects. Gate-bearing Preflight SHALL retain
exactly `PASS` and `BLOCKED` results.
`FULL_PREFLIGHT` and `FOCUSED_RECHECK` are Review modes;
`CONTROL_PLANE_ADJUDICATION` is an existing-control-plane convergence route
outside Preflight Review, not a Review mode or canonical state.

The first review in a lineage SHALL be `FULL_PREFLIGHT`, cover the complete
prescribed matrix and an independent adversarial probe, and attest that all
findings reasonably discoverable from supplied evidence were reported. Every
blocking finding SHALL prevent execution.

A revised artifact MAY use `FOCUSED_RECHECK` only when mechanical self-check
passes; the same independent reviewer instance continues; scope, contract/spec,
acceptance, risk/evidence profile, authority, assignments, allowed/forbidden
files, branch/worktree, database/production, and Git/publication/deployment
boundaries are each verified unchanged; and the diff is limited to declared
finding corrections plus necessary adjacent edits.

The existing Preflight Review artifact SHALL record mode; safe project-relative
root/current artifact paths and whole-file SHA-256 values; safe project-relative
parent Review path and whole-file SHA-256; attempt; exact reviewer product,
contract-local instance ID, role, and capability profile; a same-reviewer value
derived from immutable parent identity; an explicit protected-boundary checklist;
declared finding IDs and section anchors;
mechanical evidence; completeness; blocking findings; and recommendations. SHA
values SHALL cover whole regular-file bytes exactly as stored without newline
normalization. Root/current paths SHALL be identical logical paths; path drift
and same-hash substitution at another path are invalid. Current SHA SHALL match
the current regular non-symlink file. At full root, root/current SHA values SHALL
match; after correction, the verified immutable parent Review SHALL anchor the
historical root SHA and reviewer identity without requiring historical bytes at
the mutated path. Every evidence reference SHALL resolve to a regular non-symlink
file within project root. Missing legacy fields SHALL select full review.
Invalid revision/parent binding, replacement reviewer, reviewer identity reused
from author/executor, changed boundary, or undeclared diff SHALL prevent focused
eligibility. This Review
evidence SHALL NOT become a schema, Handoff field, task ledger, or canonical
state.

After two blocked Review results in one lineage, reviewer conflict, expanding
correction scope, an unauthorized protected-boundary change, or a late ordinary
finding that should have been detected during full review, the workflow SHALL
route to `CONTROL_PLANE_ADJUDICATION`. An already-authorized boundary change
SHALL start a new lineage at full review; an unauthorized change SHALL remain
`BLOCKED` until adjudicated and then, if authorized, start a new full lineage.
Adjudication MAY permit one terminal focused recheck after one consolidated
correction bundle; terminal failure SHALL not reopen an unlimited loop.

A non-blocking recommendation SHALL be optional and SHALL NOT contradict
acceptance, safety, authority, evidence integrity, or deterministic execution.
A non-actionable observation with actual residual risk SHALL remain separately
classified as accepted residual risk with impact and owner or decision; it SHALL
NOT be relabeled as a recommendation or unresolved actionable finding. P0/P1,
security, integrity/data-loss, authority, scope, contract, risk, acceptance,
forbidden-effect, false-evidence, and non-executable-plan findings SHALL remain
blocking in every mode.

#### Scenario: First review is complete

- **WHEN** a Plan or Brief enters its first Preflight in a lineage
- **THEN** `FULL_PREFLIGHT` covers the complete matrix and adversarial probe
- **AND** reports all reasonably discoverable findings with completeness true

#### Scenario: Same-scope mechanical correction

- **GIVEN** a full review reported a bounded finding set
- **AND** the same reviewer and every protected boundary remain unchanged
- **WHEN** mechanical self-check passes and the diff only closes those findings
- **THEN** the next Review uses `FOCUSED_RECHECK`
- **AND** unaffected full-review work is not replayed

#### Scenario: Protected boundary changes

- **WHEN** any protected boundary or reviewer instance changes
- **THEN** focused eligibility ends
- **AND** an authorized revision starts a new full lineage while an unauthorized
  revision remains blocked for adjudication

#### Scenario: Legacy Review lacks convergence fields

- **WHEN** historical Preflight Review evidence lacks the new record fields
- **THEN** it remains historical evidence
- **AND** the next Review uses `FULL_PREFLIGHT`

#### Scenario: Safety finding appears during focused review

- **WHEN** focused review identifies P0/P1, security, integrity/data-loss, or
  authority risk
- **THEN** Preflight is `BLOCKED`
- **AND** completeness and retry limits do not suppress the finding

#### Scenario: Reviewer serially adds earlier-discoverable finding

- **GIVEN** full review attested completeness
- **WHEN** focused review adds an ordinary finding already discoverable in the
  root revision and not caused by correction
- **THEN** it records a completeness breach
- **AND** routes to adjudication instead of another serial Review loop

#### Scenario: Two blocked rounds do not converge

- **GIVEN** one full Review and one focused recheck are both blocked
- **WHEN** another retry would begin
- **THEN** control-plane adjudication consolidates the decision
- **AND** at most one terminal focused recheck may follow

#### Scenario: Non-blocking recommendation

- **WHEN** optional improvement affects no acceptance, safety, authority,
  evidence-integrity, or execution requirement
- **THEN** Review records impact and owner/decision
- **AND** recommendation alone does not change `PASS` to `BLOCKED`

#### Scenario: Non-actionable residual risk remains distinct

- **WHEN** Review observes actual residual risk that requires no current change
- **THEN** it records accepted residual risk with impact and owner or decision
- **AND** it is neither an optional recommendation nor unresolved finding

#### Scenario: Later Reviews remain mandatory

- **WHEN** Plan Preflight passes
- **THEN** profile-appropriate verification and Implementation Review remain
  mandatory
- **AND** completion still requires fresh final verification, Final Review, and
  Completion Contract

#### Scenario: Local compact exception does not create synthetic lineage

- **WHEN** local work satisfies the compact Direct Change exception
- **THEN** its inline readiness and self-review do not create a standalone
  Preflight or hashed Review lineage solely for bookkeeping
- **AND** external or protected work cannot inherit this exception
