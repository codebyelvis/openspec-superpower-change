## ADDED Requirements

### Requirement: Native projections bind exact single-file candidates

An approved native consumer adaptation SHALL bind every exact destination,
file type, preimage SHA-256, original mode, owned text, preserved-byte digest
and candidate SHA-256. Multiple changes to the same native file SHALL use one
combined candidate or a freshly approved successor prestate. Native projections
SHALL reuse the existing managed-block primitives without extending or
retargeting the four-product portable manifest. Unowned personal rules,
frontmatter and explicit project document ownership overrides SHALL remain
unchanged. Specific approval and executable Preflight PASS SHALL precede native
mutation; advisory inputs and the prior source-slice approval SHALL NOT suffice.
The preserved-byte digest calculation SHALL bind its exclusion boundary and
encoding. An unchanged managed body excluded from that digest SHALL separately
retain byte-equality and canonical-parity evidence, so a matching outside-body
digest cannot conceal managed-body drift.

#### Scenario: Claude receives CCG and report path qualification

- **WHEN** one approved change appends CCG and qualifies the native path clause
- **THEN** both edits bind one original preimage, candidate and per-file receipt
- **AND** a second apply cannot reuse the old preimage hash
- **AND** the existing 0600 mode and unowned protection text remain unchanged

#### Scenario: Native prestate drifts before replacement

- **WHEN** destination bytes, mode, type or bound identity no longer match
- **THEN** apply stops before mutation and blocks later destinations
- **AND** backup or recovery cannot silently adopt or overwrite the drift

#### Scenario: Grok outside-body digest excludes unchanged CCG

- **WHEN** the digest removes the original managed body as well as exact-text edit spans
- **THEN** the calculation preserves both literal markers and every other remaining byte
- **AND** the unchanged CCG requires independent original/candidate byte equality and canonical parity

### Requirement: Native projection acceptance follows actual consumption

Acceptance SHALL distinguish actual launcher and configuration root from file
and product counts. Default Codex and alternate account A SHALL be assessed
separately. Claude launchers SHALL retain distinct authentic session evidence
and real product identity. Cursor IDE and CLI SHALL remain separate acceptance
scopes. Claude/Cursor projection checks SHALL include Grok transitive consumption
when compatibility discovery applies. File parity, help output, host catalogs,
inspect registration and correct classification alone SHALL NOT establish native
body loading, behavior, assignment authority or seven-name equivalence.
Pre-write evidence SHALL be labeled `event-mechanism-qualified`; post-write
candidate source/loading and behavior evidence SHALL be labeled
`native-load/behavior-accepted`. These labels SHALL NOT add canonical states or
Handoff fields. Old-config mechanism qualification SHALL NOT substitute for
candidate acceptance, and missing mechanism qualification SHALL block writes
to targets consumed by that entry.

#### Scenario: Shared catalog lists a skill for account A

- **WHEN** shared discovery appears in the current host catalog but no account-A CLI loading event is observed
- **THEN** evidence may report host discovery and private-directory absence
- **AND** CLI loading and authority qualification remain unproven

#### Scenario: Grok can consume revised Claude and Cursor rules

- **WHEN** a native projection changes Claude or Cursor files discovered by Grok compatibility
- **THEN** acceptance assesses Grok as an affected consumer
- **AND** unknown source loading cannot be replaced with a publisher registration flag

#### Scenario: Old-config source diagnostics succeed

- **WHEN** a native diagnostic assembles existing global instructions before the candidate is installed
- **THEN** it may support the applicable source-observation mechanism's qualification
- **AND** new-candidate loading and behavior remain pending until fresh post-write acceptance

### Requirement: Native report projections stop incompatible publication

Native delivery SHALL preserve advisory chat, authorized unbound advisory
persistence and immutable formal-attempt evidence as separate contracts.
Only authorized unbound advisory output MAY choose a compatible publisher
session destination. Bound paths or first-line formats incompatible with the
publisher SHALL stop publication without renaming, rewriting or directly
writing protected evidence. Publisher implementation and its Claude launcher
whitelist SHALL remain unchanged in this native projection slice.
Personal conversational prefix rules SHALL remain unchanged but SHALL NOT
alter the exact bound report first line; formal-body checks SHALL reject such
prefix contamination without deleting the personal rule.

#### Scenario: Companion attempt matches protected review filename

- **WHEN** a bound formal attempt ends in `-review.md` and the publisher cannot represent its path or first-line contract
- **THEN** the consumer reports the publication conflict and stops
- **AND** it cannot rename the attempt, prepend publisher metadata or bypass the direct-write guard

#### Scenario: Native Grok requests Claude publication identity

- **WHEN** Grok attempts to use a publisher accepting only claudex or claudeg
- **THEN** the launcher mismatch is rejected without expanding the whitelist
- **AND** advisory chat remains distinct from formal evidence acceptance

#### Scenario: Conversational prefix contaminates formal report

- **WHEN** an attempted bound Review body begins with `亮哥：# Review Result: PASS`
- **THEN** its first line fails the exact formal Review contract
- **AND** the report is not accepted, renamed or silently rewritten to conceal the mismatch

### Requirement: Native recovery and unresolved mechanisms stay explicit

Before native writes, the approved execution package SHALL supply reviewed
recovery commands, backups outside discovery, original-mode restoration and
isolated failure evidence. Current-file drift SHALL stop recovery rather than
overwrite unrelated changes. Required native source/event mechanisms SHALL
be qualified before live acceptance. Unverified Superpowers dependency changes,
Grok single-hook isolation, supplier-wide hook switches and unpinned open-source
trials SHALL remain outside this six-file projection slice.

#### Scenario: Backup restoration command has not been verified

- **WHEN** only a design or candidate hash exists and no accepted recovery command or negative test evidence exists
- **THEN** Preflight remains blocked and no HOME destination is mutated

#### Scenario: Single-hook exclusion has no stable compatible key

- **WHEN** Grok documentation describes individual toggles without a verified guard-specific key and recovery mechanism
- **THEN** the selective hook change remains separately blocked
- **AND** disabling every Claude hook or all unmanaged hooks cannot substitute for it
